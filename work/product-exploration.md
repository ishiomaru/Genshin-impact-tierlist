# 原神Tier研究からの製品探索と採択

2026-10-29。**推奨は「戦力比較・編成配分ワークベンチ」。用途から候補を比べ、具体的な4人編成を仮置きし、支援の重複・不足を確認して比較へ戻る道具に育てる。** Tierは候補を理解する入口、完成した計画は利用者が得る成果物とする。元Markdownは最初の研究データであり、製品の完成仕様にはしない。

ユーザーの選好確認への回答は「A,Bは両方とも重視したい」。これを採択の重要な条件として反映した。Cの研究ノートを独立した主製品にするより、Aの比較とBの配分を一続きの仕事にし、根拠・版管理はその判断を支える基盤に置く。これは利用者需要の実験結果ではなく、今回の依頼者の優先順位と実現性からの選定である。

## 1. 解くべき仕事と、現状からの出発点

対象利用者の仮説は「高難度のために候補の違いを理解し、複数編成の支援を配分したいプレイヤー」。単に一番上のキャラを知りたい人、全装備を最適化したい人、理論検証を投稿したい人では仕事が違う。今回、利用者インタビューや市場規模の調査はしていない。

原文には77運用の点数・短評・制約・代表編成・出典がある。v1はそれを忠実に探索できる一方、390px幅では検索がY≈902、最初のカードが≈1005。比較の支援注意は≈4182にあり、読んだ後の配分判断は利用者に残る。完成版を壊す必要はないが、画面装飾やフィルターの追加だけでは仕事が完結しない。[監査の根拠](v1-audit.md#3-実画面と操作から分かった問題)

この製品での一連の行動を次のように仮置きする。

```text
攻略したい用途・比較条件を選ぶ
  → 候補の評価・制約を比較する
  → 具体的な代表編成を計画に仮置きする
  → 重複／不足／未確認を見つける
  → 別候補・別の代表例を比較する
  → 前提と残る確認事項付きの計画を保存・共有する
```

「評価が高い」と「自分の所持条件で組める」と「特定の敵を攻略できる」は別の判断として、画面でもデータでも分ける。

## 2. 探索した方向性

試作前に重視したのは、①根拠のある回答への到達、②適用外の見分け、③現在のデータで成立し更新できること、④再訪理由、⑤狭い画面での中心操作。総合点や機能数は付けない。色・余白の違いではなく、利用者が完成させる仕事を変えて比較した。

### A：モード・レンズ — 条件を変えて評価を理解する

| 観点 | 構想 |
|---|---|
| 利用者・問題 | 複数候補から高難度向けの戦力を見極めたい人。単一の総合Tierでは違いや適用条件が見えない |
| 中核体験 | 用途を選ぶ→同軸で比較→何の条件が違いを生むか確かめる |
| 原文にない価値 | 元の点数の1軸±0.5の感度、手持ち条件との適合／適用外の可視化。将来は比較理由を保存 |
| UI/UX | 共通軸の数値・短い制約・比較表。大きな導入より比較を先に置く。モード配分と、実際の凸・敵の条件を別にする |
| データ・技術 | 現データと純粋な再計算で成立。条件セットと適用範囲を追加。任意凸のTierを作るには現データが不足 |
| 開発・運用の代償 | 比較軸・短評・例外の編集が必要。点数や閾値の変更は全比較へ影響する |
| リスク・検証 | 操作できると実測に見える、序数の小数が精密さに見える。重みと点数変更を区別する理解課題で確認 |

### B：編成配分台 — 手元の資源から複数編成を組む

| 観点 | 構想 |
|---|---|
| 利用者・問題 | 螺旋2編成・幽境3編成等を検討する人。高評価の前衛を集めても支援が競合し、同時に組めない |
| 中核体験 | 所持と具体例を選ぶ→複数編成へ割り当てる→競合・不足を解く→計画を残す |
| 原文にない価値 | 名前の共起ではなく、固定された4枠の同一キャラ照合。所持・凸条件の不足と未入力の区別。将来は検証済みの代替レシピから探索 |
| UI/UX | 編成ごとの4枠、共有される支援、衝突箇所への直接操作。PCは配分と候補を同時に、モバイルは対象枠を維持して往復 |
| データ・技術 | 固定例の集合照合は容易。汎用の推薦にはキャラID、役割、代替型、必要条件、生存枠、敵条件が必要。本文を名前で分割するだけでは不足 |
| 開発・運用の代償 | 「代表例のカタログ」を継続編集する費用が中心。条件違いを抱えた全組合せの再計算は大きい。所持情報の移行・保存も必要 |
| リスク・検証 | 重複なしを攻略可能と誤認、支援不足を勝手に代替して性能を保証する危険。衝突・不足・未確認・条件外を含む実例で確認 |

### C：判断の研究ノート — 根拠・異論・更新を追う

| 観点 | 構想 |
|---|---|
| 利用者・問題 | 納得して評価を使いたいプレイヤーと研究編集者。参照URLだけでは何を確かめ、何が変わったか分からない |
| 中核体験 | 疑問を選ぶ→主張・条件・根拠の範囲を追う→版に結びつく判断メモを保存する |
| 原文にない価値 | 主張単位の照合状態、採用・不採用理由、将来の意味差分と再確認の対象。根拠の依存元を追い、転載を独立証拠に数えない |
| UI/UX | 問いから入る短い結論、出典と留保が隣り合う証拠の流れ。全文やリンク集を先頭にしない |
| データ・技術 | 3事例で成立。Claim–Evidenceの対応、取得日、対応版、レビュー者が必要。現状は原文1版のみで、実在する改訂差分はない |
| 開発・運用の代償 | 自動収集だけでは成立せず編集・検証担当が必要。鮮度の表示が運用責任になる。読みたいだけの人には過重 |
| リスク・検証 | 本文取得を主張の検証と誤認、証拠がないのに履歴を演出、説明の長大化。範囲の言い換えと更新演習で確認 |

### D：再現計算ラボ — 編成・装備・回しを計算する

| 観点 | 構想 |
|---|---|
| 利用者・問題 | 投資や装備の差を数値で比べたい高度な利用者。原文の序数では答えられない |
| 中核体験・追加価値 | 入力条件を固定して計算し、結果と再現設定を共有。DPSだけでなく反応・エネルギー・時間を検査 |
| 実現性・UI | [gcsim](https://docs.gcsim.app/)や[Genshin Optimizer](https://github.com/frzyc/genshin-optimizer)は隣接する計算・最適化領域をすでに扱う。自作の数値モデルより、限定ケースの入力・比較・再現連携を先に検討する |
| データ・構成・代償 | 対応キャラ・反応・装備、回し、敵、乱数、計算エンジン版、実行条件が必要。未対応・計算時間・運用費を調査する必要がある |
| リスク・検証 | 対応不足や理論と実戦の乖離。3件程度の既知設定の再現と結果差の説明が先。今回は再シミュレーションしていない |

Dは有力な将来方向だが、今の不確実性は画面より計算モデルの対応・再現性にある。架空のDPSを載せる試作は作らず、今回の主製品には採択しない。

## 3. 参考事例から採用する原理

詳しい確認内容・取得できなかった資料は[調査記録](exploration/sources.md)。外観ではなく、情報と操作の対応を参照した。

- gcsim：**結果を再現入力と結びつける。** 保存・共有の単位を「Tier画像」ではなく「編成・条件・評価版付きの計画」にする。[開発者の導入説明](https://docs.gcsim.app/get-started/)
- Genshin Optimizer：**個人の入力と一般データを分ける。** 所持・装備の入力境界を作り、既存の入力形式と将来つなげる。装備最適化を今回そっくり再実装しない。[開発リポジトリ](https://github.com/frzyc/genshin-optimizer)
- OWID：**結果の近くに定義・単位・期間・出典を置く。** 共有・書出しにもメタデータを残す。原神の序数を連続的な性能時系列へ読み替えない。[データページ](https://ourworldindata.org/grapher/life-expectancy)、[Chart API](https://docs.owid.io/projects/etl/api/chart-api/)
- KQM：**個別資料の対応版とサイト全体の更新を分ける。** ソースの取得成功だけで計画を最新としない。[更新履歴](https://keqingmains.com/changelog/)、[個別ガイド](https://keqingmains.com/q/neuvillette-quickguide/)

Enka.Networkは公開Showcaseの入力候補だが、全所持の証明にはならない。導入するなら利用者の明示操作、TTLに従うキャッシュ、429・非公開・障害の表示、手入力への復帰が必要。今回APIで所持情報を取得していない。[開発者資料](https://github.com/EnkaNetwork/API-docs/blob/master/api.md)

### 新しい算術分析から得た設計上の示唆

**原著者の評価を正解と仮定せず、モード点の置き方にどれだけ依存するか**を調べた。重みは固定し、1回に1軸だけ±0.5（0〜5の範囲）を仮置きして、元の閾値でTierを再計算する。

| 重み | 少なくとも1つの仮置きでTierが変わる運用数 / 77 |
|---|---:|
| 基準 45 / 35 / 20 | 59 |
| 螺旋重視 60 / 30 / 10 | 72 |
| 幽境重視 30 / 60 / 10 | 72 |
| シアター重視 30 / 20 / 50 | 66 |

再現：[analyze-data.mjs](exploration/analyze-data.mjs)、[全出力](exploration/evidence/data-study.json)。検算例：サンドローネの基準4.600は螺旋点だけ5→4.5で4.375となりSS→S。ヌヴィレットの4.250は螺旋点4.5→5で4.475となりS→SS。スクロースの3.900は螺旋点4→3.5で3.675となりS→A。

これは**今回の算術による感度検査**であり、59運用の評価が間違い、変動確率が59/77、原著者の確度が低い、という意味ではない。1軸0.5が妥当な誤差幅という実証もない。設計上は、Tierを細かい順位や個人条件の自動減点へ発展させるより、モード別評価・適用条件・編成成立の問題を別々に見せる方がよいという示唆を得た。既存の10/14/28という「固定点数で重みを変える分析」とも区別する。

### 外部確認の具体例

G14の[公開計算](https://gwisted.com/games/genshin-impact/calculations/510c773f-db9e-4428-a4aa-0f93aa8cdf63)で、180.56K・20秒・八重C1・七七C2を本文確認した。原文の全員無凸条件に直接移せないという指摘はこの範囲で確かめられる。一方、DPS再現もサンドローネSSの独立検証も実施していない。取得した値をスコアや標準編成へ自動混入しない。[確認範囲一覧](exploration/sources.md#原文の根拠を抜き取りで確認した範囲)

## 5. 採択と、あえて犠牲にするもの

**A＋Bを採択する。Aで候補の理由を理解し、Bで実際の計画を組み立てる。中心は常に「比較に戻れる編成配分」であり、独立したダッシュボードを寄せ集めない。**

理由は以下の通り。

- ユーザーのA/B両方を重視する意向に合う。Bだけでは候補を選ぶ根拠が不足し、Aだけでは比較後の行動が終わらない。今回の統合試作で、同じ条件・選択対象を保った往復が実装可能だと確認した。
- 原文の特徴である「完成編成」「専用支援」「モードによる評価の違い」を、別々の注意書きから中心操作へ変えられる。研究の強みを使いながら、原文にはない計画作成の価値を追加できる。
- 原文の順位を個人向けに勝手に計算し直さず、確かな集合照合と条件の確認から価値を出せる。最適化エンジンや全面的なDPSモデルを初期の前提にしなくてよい。
- 更新対象を評価・代表編成・成立条件へ分解すると、追加研究を新しい候補として継続提供できる。保存計画への影響を知らせる再訪理由も生まれる。ただし、その需要と編集費用はまだ検証が必要。

犠牲にするもの：

- 初期版の軽い「一覧だけ見る」体験に比べて入力と状態が増える。閲覧専用の一覧入口は残すが、全情報を一画面へ詰めない。
- すべてのキャラ・任意4人編成・凸・装備を初回から最適化することは捨てる。編集済み代表例を軸にした範囲を明示する。
- Cを主製品にした場合の研究管理・投稿・議論の深さは優先しない。主張別の根拠や更新状態は、比較や計画の必要な場所から開ける範囲で始める。
- Dの投資効果や精密なDPS比較は返さない。将来の独立した計算ケースとしてのみ接続する。
- アカウント・クラウド同期・自動データ収集を最初の価値にしない。所持入力と端末内保存が使われるかを先に確かめる。

## 6. 採択案の製品目標と中核機能

**目標：利用者が、比較の理由と残る不確実性を把握した複数編成の検討案を作り、同じ前提で再開・共有できる。** 成功は画面数・滞在時間・機能数より、判断の完了と誤解の少なさで見る。

最初の製品範囲案は次の通り。件数は開発スコープの提案であり、現在実装済みという意味ではない。

| 中核 | 必須の振る舞い | 初期の範囲 |
|---|---|---|
| 条件つき比較 | 同じ尺度の評価、主要制約、原文条件の適用／適用外、NRの理由に到達する | 元の77運用の閲覧と、選択した2〜3候補の比較。未知条件のTierを生成しない |
| 具体編成の配分 | 個別の4枠を選び、同一キャラの重複、所持不足、凸条件外、未確認を区別する | まず10〜15程度の編集済み代表例で2編成の経路を完成させる。その後3編成へ。任意の代替候補を自動生成しない |
| 比較と配分の往復 | 計画の対象枠を保持し、別候補を仮置きする前に競合・条件を確認できる | PCの同時表示とモバイルの対象枠付き切替。保存前の一時変更を明示 |
| 再現できる保存・共有 | 評価版・モデル版・編成例版・比較条件を保つ。復元できない状態は黙って最新へ読み替えない | 端末保存、JSONの書出しと読込、個人メモを除く共有。同期は後段 |
| 根拠と更新 | 出典の採用範囲、未検証箇所、更新で計画に影響する理由を示す | 重要条件に絞る。実在する過去版ができてから履歴を表示 |

## 7. 新たに必要なデータと判定ルール

| データ | 最小の形・取得方法 | 検証と注意 |
|---|---|---|
| Character / Operation | 同一キャラの安定ID、表示名・別名、運用ID、役割、採点対象／NR | 別運用でも同じキャラは同時使用できない。名称ハッシュだけに依存せず、改名マッピングを持つ |
| Assessment / ConditionSet | 出典版、著者、モード点、適用する凸・育成・武器等、評価モデル版 | 原文の評価と新たな編集評価を別レコードにする。代表編成ごとのDPS評価だと誤認させない |
| TeamRecipe | 固定4枠、役割、凸等の必要条件、生存手段、採用根拠、確認版、代替型との関係 | 「A／B／C、またはD＋異元素2枠」を全組合せに展開しない。具体枠が確定した型だけ入力。原文代表例も統一実測済みとはしない |
| Roster | キャラ別に所持／未所持／未入力、凸・育成の既知／不明、取得元と時刻 | 空欄を未所持としない。Showcaseは全所持一覧ではない。任意のGOOD入力も網羅性の確認が必要 |
| Plan | 対象用途、2/3編成、選択レシピと版、比較候補、利用者の留保、保存時の各版 | 所持情報と公開用の計画を分離。元の評価が更新されても保存時の判断を再現できるようにする |
| Source / Claim / Revision | URL、対応版、取得日時、採用する主張、支持／反例／条件差、レビュー状態、変更理由 | 取得成功と検証済みを別フィールドにする。共通の元情報・転載関係を可能な範囲で記録 |

新規計算はまず以下に限定する。

1. 原文の序数に対する重み付けと、明示した感度検査。元の評価は保存し、仮置き計算を混ぜない。
2. 具体4枠のキャラID集合の交差。同一編成内の重複と、複数編成間の重複を別検査。
3. 所持・凸等の条件に対する「満たす／満たさない／未確認」の3状態の判定。満たすことは攻略成功の保証ではない。
4. 編集済みレシピの候補探索。最初は条件に合う組合せを列挙する範囲とし、**序数をチーム間で足して「最強」を決めない**。大量化したときだけ探索打切り・Worker等を測定して判断する。

幻想シアターの期別元素・活力・複数公演の状態は、同時2/3編成の集合照合とは別モデル。Aの比較視点として残しても、Bの割当でシアター攻略を判定したことにしない。

## 8. 主要な画面・操作とUI/UXの方向

| 画面・状態 | 主要な行動と設計課題 |
|---|---|
| 入口 | 「候補を比べる」「保存した計画を再開する」。研究版・用途を短く提示。検索のために大きな紹介部分を毎回通らせない |
| 比較 | 2〜3候補のモード評価、役割、最重要条件を同じ行・軸で読む。短い制約の語彙は編集し、原文へ戻れるようにする。条件外でも元の参考評価として読める |
| 計画ワークスペース | 選択中の編成枠、具体4枠、競合の相手を見える状態にする。候補を見ても選択対象と比較視点を失わない。未入力を安全な初期値にする |
| 所持・条件入力 | 最初に全所持を要求せず、計画に関係するキャラから入力可能にする。手入力とインポートを混ぜる場合は出所・上書き優先を確認 |
| 根拠パネル | 結果の横から開き、何を支持し何は未確認かを表示。Cの長文全体を毎回読ませない。閉じると元の対象・スクロール・フォーカスへ戻る |
| 更新・復元 | 最新版の再評価と保存時の状態を並べ、変更理由と確認が必要な枠を示す。消えたレシピ・改名・壊れたJSON・保存拒否にも再開経路を作る |
| モバイル | 配分と比較を上下に置くだけでは長い。対象枠を示す短いトレイと比較面を切り替える案、2候補ずつの要点比較を次に実画面で比較する。仮置き時に結果へ戻れることは今回確認済み |

視覚の独自性は、4枠の分担・取り合う支援・条件差という情報の形から作る。画像は本人識別、罫線や色は対応関係に使う。色だけで競合・未確認を示さず、文字ラベルを併用する。動きは仮置き先や競合の変化の理解に使える場合のみ検討し、静止状態でも理解できるようにする。

## 9. アーキテクチャ上の重要な判断

| 論点 | 初期の推奨 | 再検討する条件・代償 |
|---|---|---|
| 既存スタック | React / TS / Viteを代表経路の土台として使う。比較・計画・所持・保存・評価を機能単位に分け、純粋な判定層をUIから独立させる | 探索を理由にフレームワーク全面移行を始めない。個別ページの検索流入が必須なら、静的HTML生成・メタ情報の方式を小さなADRと実装比較で決める |
| データの正本 | バージョン付きの評価・レシピ・条件を、検査可能なJSON等で管理。原文は不変の入力スナップショット。生成した検索索引・表示データと分離 | Markdownの固定段落から最新状態を毎回推測しない。編集UI/CMSは編集頻度と担当者の負担を確認してから |
| バックエンド | 初期は公開データをビルド時に配信、個人計画は端末内。リアルタイムAPIなしでも中心体験を成立させる | 多端末同期、共同編集、公開計画の永続IDが利用されるならAPI＋DBを追加。認証・権限・復旧の運用費が増える |
| 保存 | スキーマ版付きのStorageAdapter。小さな計画はlocalStorageでも始められる。実体が大きくなればIndexedDBを比較 | 移行、容量拒否、破損、他タブ、書出し・読込の仕様が必要。元の`teyvat-atlas-v1`を読み替える場合は明示的な移行を設ける |
| URL・共有 | 安定した運用／レシピID、比較条件、資料・計算モデル版を含める。所持・メモは標準共有に含めない | URL長が実用を超えたときにサーバー保存リンクを検討。古い版を取得できない場合の失敗・最新で開き直す導線を作る |
| 外部情報 | 必要なメタデータを版固定で取り込み、UI表示時は欠損しても使える。個人API連携は明示操作とキャッシュを設ける | Enkaは任意の部分入力。原文評価・所持・外部統計を同じ値で上書きしない。利用条件・アセット権利は公開判断時に確認する |
| 計算 | 重みと制約照合は端末内の決定的な関数。DPSの計算ケースは別のデータ型・版・検査にする | シミュレーションを足す場合は対応一覧・既知ケース・敵条件・エンジン版・実行コストを先に検証する |

## 10. 継続更新・運用と開発基盤

更新の単位は「最新のTier画像を生成すること」ではなく、**条件・代表例・根拠のどこが変わったかを採択すること**。

```text
公式告知・ガイド・編集上の発見
  → 取得時点と対応版を記録
  → 前の公開スナップショットとの差分を作る
  → 影響する評価・条件・レシピを抽出
  → 編集者が採用範囲を判断（必要なら計算・実戦確認）
  → データ・画面・保存計画への影響を検査
  → 公開用スナップショットを確定し、前版を保持
```

初期運用は少人数向けのGitベースでよい。編集担当は条件・レシピ・根拠を確認し、レビュー担当は数値と表示への影響を確かめる。小規模なら同一担当でもチェックリストを残す。担当者と無理のない頻度は未決定であり、「毎パッチ自動で正しい」と約束しない。更新が止まった項目は確認版と未再検証の状態を表示する。

Git・CIの次の単位：

- 現在のv1を基準として保持。生成物・依存ディレクトリの追跡解除は別の小さな変更でレビューする。今回、追跡解除・コミット・pushは行っていない。
- lockfile、Node/Pythonの実行版、クリーンな`npm ci`、原文アダプター、次期データのスキーマ・参照整合性、型・ビルドをCIで再現する。
- 評価計算の期待値、同一キャラの別運用・代替型・所持未入力の判定、古い保存データの移行を検査する。実装と同じ式を写しただけのテストを増やさない。
- Playwrightで「比較→仮置き→競合解消→保存→復元」の代表経路と、保存拒否・欠損レシピ・版不一致を検査。ブラウザはCIで取得できる版を固定し、MacのChromeチャンネル前提を外す。
- 公開候補ごとにPC・390・320pxの代表状態を画像で確認。自動アクセシビリティに加え、キーボード・実機・支援技術は別の検査として実施する。
- 外部資料のリンク状態は公開判定の唯一のゲートにしない。429等で失敗した記録と、内容の再確認を分ける。依存更新は小さく検証して採択する。

| 段階 | 具体的な成果物 | 次へ進むための確認 |
|---|---|---|
| 0：対象とデータ契約 | プレイヤーの代表課題、安定ID・評価／条件／レシピ／所持／計画のスキーマ。編集済み代表例10〜15件と、原文・外部照合の範囲 | 別運用の同一キャラ、未入力、★4低凸、曖昧な代替、支援重複をデータで区別できる。編集者が1件を追加・変更する演習で負担を記録。供給できなければ自動推薦の範囲を縮める |

段階0〜1が次の設計作業。今回の試作コードをそのまま本実装へコピーすることや、全データを一度に作り直すことを引き継ぎ方にしない。

## 12. 未解決事項と、判断を変える検証

| 不確実性 | 次に行う検証・採択を見直す条件 |
|---|---|
| A＋Bが実利用で価値を生むか | 高難度の複数編成を検討するプレイヤー5名程度に、「候補の違いを説明→支援重複を解く→計画を再開」を依頼。正答・未完了・手戻り・負担を記録。需要は今回未測定 |

| モバイルの往復負荷 | 2候補の要点表＋対象枠トレイと、配分／比較の面切替を実物で比較。所要時間は成功・未完了を分け、同じ問題を繰り返して覚える効果を避ける |
| レシピの更新費用 | 編集者1名が実在する変更を1件反映し、条件・根拠・計画影響のレビューまで実施。時間と詰まりを測る。継続できないならカタログを限定し、自動推薦を広げない |

| 運用の責任・公開範囲 | 編集担当・頻度、非公式素材の扱い、ホスティング・同期が必要かは次段階で具体的に決める。今回、公開・課金・外部個人データ送信・Git公開操作は行っていない |
