# 品質評価と改善の手順

評価は、合格条件、品質の比較、残る不確実性に分ける。点数は話し合うための目安であり、物理量や統計的確率ではない。

## 1. 先に確認する合格条件

| 条件 | 検査 | 不合格の例 |
|---|---|---|
| 意味が保たれる | 重要な主張、条件、留保、数値、出典を素材と照合 | 推測を確定事実として追加。序数を火力倍率に変換 |
| 重要情報へ到達できる | 内容対応表から画面までたどる | 原文を添付しただけで、再編集した画面から条件に気付けない |
| 主な行動が成立する | 検索・比較・詳細・戻る等を実行 | 見た目だけの操作部品。空状態から戻れない |
| 対象環境で読める | 狭い画面、長い項目名、キーボード、拡大等を確認 | 本文全体が横にはみ出す。焦点が見えない・閉じられない |
| 素材と表示の由来が適切 | 画像・図・データの出所と表示文脈を確認 | 挿絵を実際の証拠として示す。使用条件が不明の素材を確定採用 |

重大な違反は、見た目の高評価で相殺しない。原文自体に疑義がある場合は、原文の判断として表示するか、追加調査を行うかを明示する。忠実な転記を外部妥当性の証明にしない。

## 2. 完成度を比べるための観点

各軸を1〜4で記録するなら、下の目安を使う。合計点は必須でない。分からない場合は未評価とし、理由を残す。

| 軸 | 1：問題が大きい | 2：部分的に成立 | 3：十分に成立 | 4：特に優れている |
|---|---|---|---|---|
| 情報の発見 | 重要情報の場所が分からない | 手間や戻りが多い | 主な課題へ迷わず進める | 初見・再訪・深掘りの各入口が適切 |
| 理解・説明 | 重要な誤解を生む | 読めるが関係を自力で組み立てる | 要点と条件の関係が伝わる | 比較・反例・前提まで自然に確かめられる |
| 視覚の完成度 | 階層・余白・文字・素材が崩れる | 基本は整うが密度や表現が不揃い | 主題に合い、細部まで一貫 | 強調と抑制、素材、文字組みが一体となる |
| 内容固有の創意 | どの資料にも置換できる | 固有の要素はあるが装飾中心 | 情報に対応した独自の判断がある | 読者が予想しなかった有益な見方を生む |
| 操作と状態 | 主要操作が不成立 | 成立するが発見・復帰に難がある | 入力・選択・空・詳細・戻るが自然 | 状態が予測でき、繰り返し利用も快適 |
| 全体の一貫性 | 画面や部品の関係が不明 | 個別画面は良いが移動で混乱する | 共通の語彙・視覚・操作で統合 | 複数の読み方が自然に行き来できる |

「独自性4の方が常に採用」とはしない。比較・検索が中心の道具では、慣れた部品を適切に使う判断が優れていることもある。ユーザーの好みと、内容の誤りを混同しない。

## 3. 画面の確認方法

最初の画面に加え、本文の途中、複雑な表・図、主要操作後、空状態、長い項目名、詳細から戻った状態を見る。画面幅は初期例として1440・768・390pxとし、利用対象に応じて追加する。WCAGの再配置を見る際の320 CSS px相当や200%の文字拡大は別に確認する。

画像差分は退行を見つける道具であり、正解画像を自動的に作らない。視覚レビューでは、次を実画面に結びつける。

- 最初に何へ目が行くか。それが読者の目的と一致するか。
- 重要な情報と補足に適切な差があるか。強調のせいで原文より断定的に見えないか。
- 本文・表・図・操作部の密度が、長く使っても疲れにくいか。
- 画像や動きが、理解・識別・感情的な入口のどれを担っているか。
- 日本語の文字組み、折返し、長い名称、数字の整列、余白が実内容で破綻しないか。

自動アクセシビリティ検査の検出ゼロは、全項目の適合を意味しない。図の意味が代替説明で伝わるか、キーボードの順序、フォーカスの見え方、スクリーンリーダー等は別の確認を要する。基準と実務指針は [R17,R27,R28](SOURCES.md) を参照。

## 4. 利用者の課題で見る

下記は原神資料向けの例。事実の正解は「提供資料が何を述べているか」であり、ゲームの外部事実の正解ではない。

| 課題 | 正答・成立条件 | 観測すること |
|---|---|---|
| T1：ヌヴィレットの基準とシアター重視のTier、および変更の意味を確認 | 基準S、シアター重視SS。モード点を固定した重み変更で、実測の再評価ではない | 正答、条件への気付き、所要時間 |
| T2：スクロースSが本人の直接ダメージの評価か確認 | 本人の直接攻撃だけの評価ではなく、拡散・支援で編成全体を成立させる前衛の評価 | 重要な誤解の有無、根拠へ到達したか |
| T3：SS群とヌヴィレットの評価が条件で変わる理由を説明 | モード点と重み、不完全編成への耐性等の原文の説明を用いる | 図だけ見た誤解、説明の正確さ |
| T4：171.05Kという公開DPSを確定順位へ使わなかった理由を探す | 計算条件の監査不足や比較条件の問題を特定 | 根拠を探す経路、迷い、情報の再発見 |
| T5：NRがDより下を意味するか確かめる | 前衛としての評価対象外であり、最下位という意味ではない | スコープと性能の混同 |
| T6：高Tierを並べれば複数チームが最適になるか確認 | 支援役の重複等があるため保証されない | 但し書きを読まず過信しないか |

成功率だけでなく、誤答、未完了、手戻り、主観的負担を残す。時間は正答した課題と未完了を分けて報告する。正答者だけを選ぶことで、難しい案が速く見えることを避ける。

同じ人物が同じ質問を複数案で解くと、先に内容を覚えて後の案が有利になる。順序を入れ替え、対象名や課題を同程度の別例に割り付ける。あなた一人の評価は個人適合のためには重要だが、一般の利用者への効果として統計的に一般化しない。

## 5. 人間に求める判断を小さくする

方向を比べるときは、まず同じ内容を同じくらい仕上げた案を2つ見せる。差が曖昧なら3つ目を追加する。次の質問だけで十分な場合が多い。

> この資料を使うなら、どちらを使いたいですか。A／B／どちらも違う。理由は一言でも、気になる箇所の指定でも構いません。

続いて、選んだ案で一つの実際の課題を行ってもらう。「美しい」と「調べやすい」を別々に確認する。ラベルに「高品質版」「推奨案」と書かず、順番を偏らせない。AIは回答から学ぶが、理由を勝手に過度に一般化しない。

## 6. レビュー記録の形式

```text
対象の版・画面幅：
読者課題・初期状態：
再現手順：
観測した問題：
影響／誤解：
根拠となる原文・画面：
重大度：重大／通常／細部
種類：情報／操作／視覚／好み／未検証
原因仮説：
最小の改善案：
改善後の確認条件：
結果：解消／未解消／別案を採用／提案を不採用（理由）
```

重大度は作業順序のための分類であり、数値的な尺度ではない。レビュー担当の説明を増やすことではなく、制作担当が現象を再現して直せることを重視する。

## 7. 速度と運用

Core Web Vitalsの目安はLCP 2.5秒以下、INP 200ms以下、CLS 0.1以下。実利用データの75パーセンタイル等の条件とともに読む [R29](SOURCES.md)。ローカルの一回の測定やLighthouseの総合点を、そのまま実利用の合否にしない。

開発段階では画像容量、初期表示、操作時の処理、レイアウトの変動を調べる。本番環境ではネットワーク・端末・キャッシュ条件を記録する。今回の試作にフィールド性能測定はない。

## 8. 完成と改善停止

完成版は、重要な内容の誤りがなく、主要課題と対象環境での操作が成立し、視覚・体験上の重大な問題を解消した版とする。

そのうえで「有益な改善が続かない」「改善ごとに別の損失が増える」「好みの判断以外は残っていない」場合に、候補を比較して最良版を採る。未実施検査が重要なら、完全に検証済みとは言わない。

反復回数、画像枚数、ファイル数、エージェント数、AIの自己点数、全体のコード量は、完成度の代理指標にしない。
